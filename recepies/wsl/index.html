从 Windows 配置 WSL 项目#

当 Windows 11 用户希望在 Happy Desktop 中使用 Linux 项目时，使用本操作指南。参谋长在用户授权范围内完成配置与验证，并复用已有选择。只在缺少关键选择、需要新的授权，或无法避免登录或重启时询问用户。

完整阅读部署独立远程 Agent，了解发行版下载、校验和、个人资料初始化、凭据、Tailcat 配置、连接注册以及 API 检查。使用下方 WSL 专用的账户和服务选择，而不是创建该指南中的专用服务器账户。具体请求格式以已安装的 API.md 为准。

每个环境各自安装#

  • 默认情况下，Windows Agent 管理用户的机器人及其对话。将现有机器人保留在那里。远程项目不会迁移机器人，也不会改变其工具使用的 shell。
  • 在选定的 WSL 发行版中，单独的 Linux Happy Agent 管理 Linux 项目、工作区、Git、shell 和提供商配置。将其作为普通独立远程节点连接，例如使用 wsl-ubuntu，显示名称为 Ubuntu (WSL)。
  • 桌面端通过现有连接视图访问 WSL Agent。连接 WSL 时创建项目，会在该 Agent 上注册 Linux 路径；Windows 项目仍留在 Windows。
  • 绝不能在 Windows 和 Linux 之间共享 .happy、数据库、机器人身份、Tailcat 私钥或 runtime.toml。新的远程安装会创建自己的管理用参谋长；它是独立机器人，而不是用户 Windows 机器人的副本。除非用户要求，否则日常工作中不要使用它。

控制流程如下：

Windows Chief of Staff -- wsl.exe bootstrap --> Linux Happy Agent
Windows Happy Desktop --> Windows Happy Agent
                         --> existing authenticated Tailcat connection
                             --> Linux Happy Agent --> Linux project and tools

普通机器人的 create_project、shell 和 Agent 消息工具都在其自身安装中操作。通过选定的远程连接及其文档所述 API 注册并执行远程工作；不要假设本地 Agent ID 或本地项目工具会跨安装路由。

1. 安装前先了解现状#

在 PowerShell 中检查 wsl.exe --status 和 wsl.exe --list --verbose。复用已有的 WSL2 发行版及其普通 Linux 用户。如果有多个发行版，复用用户指定的发行版，或包含目标项目的发行版；只有选择仍不明确时才询问。不要仅为了缩短命令而更改默认发行版。始终通过 --distribution 传入其准确名称。

如果尚未安装 WSL，通过一次提权的 Windows 操作安装：

wsl.exe --install --distribution Ubuntu-24.04 --no-launch --web-download

Windows 可能显示 UAC 提示。如果安装报告需要重启，记录结果，并暂停依赖后续步骤，直到用户重启；不要反复重新启动安装程序，也不要自行重启用户的计算机。重启后重新检查状态，仅在 Ubuntu 仍缺失时安装。如果虚拟化仍不可用，报告实际的 Windows 或固件要求。绝不能为解决启动错误而重置、注销或重装已有发行版。

如有需要，完成发行版初次启动时的普通用户设置。复用现有用户，不要另建一个无法访问其提供商登录信息的账户。检查 id、uname -m、$HOME、已有 Happy 进程或服务，以及 HAPPY_HOME_DIR、CLAUDE_CONFIG_DIR 或 CODEX_HOME 的覆盖设置。在 Linux 内部运行这些检查；Windows 路径或 Windows 的 HOME 不是 Linux 主目录。

使用显式参数列表：wsl.exe --distribution NAME --user USER --exec ...。对于多行初始化命令，使用已检查、采用 Linux 换行符的脚本，并显式调用 Bash。避免通过插入不可信项目路径来拼接 Linux shell 命令。

2. 以 Linux 用户身份安装#

按照远程部署指南，下载匹配的稳定版 Linux Happy Agent，并验证校验和。独立二进制程序包含自身运行时及 Linux 辅助程序；不需要检出源码、安装 Node.js、使用 Windows 可执行文件或单独安装 Tailcat。将可信的可执行文件安装到 /usr/local/bin/happy-agent；以选定的普通 Linux 用户运行，绝不能使用 root。在该发行版内安装 Git 和实际项目所需的工具。

复用已有 Linux Happy 主目录，并保留其身份。默认情况下，私有状态位于 ~/.happy，全局配置位于 ~/happy/config/happy.toml，已安装的说明位于 ~/.happy/docs。使用远程指南中的配置初始化流程，根据 Windows 参谋长的 get_local_profile 结果设置远程个人资料。已知的 Git 姓名和邮箱需单独复用。确保 Linux 用户不仅拥有 config 目录，还拥有公共父目录 ~/happy；如果仅以 root 创建内层目录，Happy 可能无法创建机器人和项目文件夹。启动前设置 [node] name = "Ubuntu (WSL)"，或之后使用受支持的 PATCH /v0/config 节点设置。桌面端使用安装自身的名称，而不是连接列表中的标签；否则 WSL 通常会继承与 Windows 相同的机器名。

对于 Ubuntu 24.04，在适用时检查文档中的 AppArmor 前置条件。测试 Linux 沙箱；不要假设 WSL 本身可以代替 Happy 的 shell 沙箱，不要全局关闭主机策略，也不要选择 Full access 来掩盖受限运行失败。

3. 复用 Linux 身份验证并选择可用模型#

提供商配置属于实际执行项目的 Agent。仅在 Windows 登录并不能让 Linux Agent 通过身份验证；连接使用的 Happy API 令牌用于认证远程守护进程，而不是支付模型推理费用。

先查找并验证选定 Linux 用户已有的提供商凭据。已经在 WSL 中登录 Claude Code 的用户，不应仅因安装 Happy 就被要求再次登录。Linux 发行版内置 Claude 运行时；只有使用 Claude CLI 获取或续期登录时，才需要单独安装该 CLI。在 Windows 的 Claude Desktop 已登录，并不代表 Linux 中的 Claude Code 已登录。

如果缺少 Linux 凭据，说明具体状况，例如：“Claude 已在 Windows 登录。请在 Ubuntu 内登录 Claude Code，才能将其用于 Ubuntu 项目。”按照官方的 Claude Code 安装说明和登录说明操作，以与 Happy 相同的 Linux 用户运行 claude。用户可能需要完成浏览器或验证码步骤。对于选定的其他提供商，使用其已安装的官方 CLI 所支持的登录流程。未经用户选择，不要把订阅访问改成付费 API 密钥访问。

如果用户改为授权将特定凭据复制到该发行版，使用远程指南中的私密传输流程，并说明续期限制。不要默默将共享的 Windows 凭据文件挂载为可写的 Linux 身份验证存储，也不要打印令牌。独立登录可以避免两个守护进程争相刷新同一个复制的 OAuth 会话。

了解现状后，通过 WSL Agent 验证用户要求的每个提供商。读取该 Agent 的模型目录，选择它实际启用的模型。Windows 机器人继续使用 Windows 模型目录；WSL 项目会话使用 WSL 模型目录。相同账户和 Happy 版本可以提供相同模型，但凭据、提供商配置和版本差异也可能导致列表不同。

4. 启动并连接 WSL Agent#

使用独立远程指南中的新 API 令牌、[feature.tailcat] 和全局配置。Tailcat 是现有的已认证远程访问路径，同一台计算机上的发行版也使用它；它需要出站连接，并会让身份验证边界可通过其地址访问。启用远程访问时需说明这一点。不要添加未经身份验证的局域网监听器、配置 WorkOS／团队模式，或另造 WSL 专用隧道。地址和令牌应保密。

只使用一个服务管理方。保留已有且正常工作的服务。对于新建、由 Windows 管理的 WSL 安装，使用一个按用户配置的 Windows 计划任务，在该用户登录时运行：

wsl.exe --distribution DISTRO --user LINUX_USER --cd ~ --exec /usr/local/bin/happy-agent run

任务使用普通 Windows 用户的交互式令牌运行，不启用最高权限，也不存储密码。使用带有 -NoProfile -WindowStyle Hidden -Command 的 PowerShell 调用 wsl.exe，然后执行 exit $LASTEXITCODE；前台调用会等待 WSL 退出。使用一个已知存在的 Windows 工作目录、显式可执行文件路径，以及正确加引号的参数。不要在任务操作中包含密钥，并避免让 Linux 继承 Windows 的 Happy／提供商路径覆盖设置。配置为无执行时间限制、允许电池供电、忽略重复启动，并设置有次数上限的失败重启。以发行版命名任务，更新前先检查已有任务，安装后启动一次。

这样会让真正的前台 Agent 由 Windows 的进程管理方保持关联，而不是添加虚假的保活进程。不要再为同一个主目录启用竞争的 systemd 单元或 happy-agent start。run 必须保持前台运行；启动守护进程后就退出的启动器无法监督它。任务失败时应报告并查看有范围限制、已脱敏的日志，而不是启动重复进程。

如果保留 systemd 服务，按照远程指南操作，并将 User、HOME、路径和服务环境改为选定 Linux 用户。已启用的服务会在发行版启动时启动；它并不保证 Windows 登录时启动 WSL，也不保证自身能让 WSL 持续运行。必须显式验证该生命周期。桌面端现有的远程连接不会唤醒已停止的发行版。参见 Microsoft 的 WSL 服务生命周期。

等待 Linux 的已认证健康检查通过、Tailcat 就绪后，从当前活跃的管理员机器人调用 set_remote_connection，在 Windows 注册准确的远程地址、端口和令牌。重复配置时复用已有连接 ID。遵循远程指南中的私密凭据处理方式和全局配置备用方式；绝不能直接编辑生成的 runtime.toml。使用连接前，必须确认其健康状态为可达、已认证且就绪。

5. 在所属 Agent 上注册项目#

Linux 项目优先放在 /home/USER/projects/...，Windows 项目优先放在 C:\Users\USER\projects\...。除非用户要求移动，否则原地复用已有项目。对于 \\wsl.localhost\Ubuntu-24.04\home\USER\projects\app 这类 Windows 资源管理器路径，选择对应发行版的连接，并在其上注册 /home/USER/projects/app。绝不能把 UNC 路径交给 Windows Agent，来代替 Linux 执行。

位于 /mnt/c/... 的项目通过 WSL 使用 Windows 文件系统，其性能和文件系统语义不同。如果用户有意选择在 Linux 中执行该项目，就以 Linux 路径在 WSL Agent 上注册。避免 Windows 和 Linux Agent 同时修改同一个检出目录。软件包安装和 Git 操作应与选定环境保持一致。参见 Microsoft 的文件系统指南。

先检查是否已注册。通过远程连接文档所述的项目 API，或在 Happy Desktop 中选中该连接后创建／注册项目。安装项目实际所需的 Linux 工具链，按配置流程操作至就绪，并在有需要时验证 Git 身份及非交互式远程访问。不要复制 Windows 的 node_modules，也不要把 Windows Git／Node 当作 Linux 工具。

6. 验证完整链路#

先使用人工构造的小型示例项目；不要仅为测试配置就把私有源码发送给提供商。通过 Windows 已配置的连接执行以下检查，而不只是从 Linux shell 检查：

  1. WSL 连接在 Happy Desktop 中可见；健康状态已认证且就绪，版本符合桌面端要求。Windows 项目和机器人仍然可用。
  2. 用户要求的提供商均通过真实推理验证，并在 WSL 模型目录中设有默认模型。缺失的凭据应明确保留为待完成的引导步骤，不能默默启用模型。
  3. 真实项目会话返回 Linux 的 pwd／uname，创建并读取一个示例文件，并通过 Happy 的 Auto 沙箱运行一次真实测试。之后确认回复、文件内容以及守护进程的健康状态。
  4. Git 状态和 Happy 的 Changes 视图都显示创建的文件。对于隔离的 Git 测试项目，先创建一个本地裸 origin 和 origin/main：Changes 会与该分支的合并基点比较。这项测试要求并不授权重写真实项目的远程仓库或分支。
  5. 没有工作正在进行时，重启选定的服务管理方。相同的远程身份、项目和对话应重新连接，后续请求也应成功。检查其他 WSL 终端关闭时的启动情况，以及事先约定的 Windows 登录／重启测试后的恢复情况；不要使用 wsl --shutdown 中断不相关的 WSL 工作。

按顺序执行文件创建及随后的 Git 检查；并行工具调用确实可能在写入完成前读到状态。Linux 沙箱可能在其用户命名空间内显示用户为 root：验证 /proc/self/uid_map 将该 UID 映射到非特权主机用户，并确认守护进程本身以该用户运行。这不会赋予命令主机 root 权限。

个人资料、提供商、项目和实际运行检查通过后，通过文档规定的 POST /v0/onboarding/complete 完成安装引导。不要让用户在桌面端重复操作。已经打开的欢迎流程会在下一次初始化时读取完成标记；最终交付时，应先完成引导，再打开远程连接。

报告发行版／用户、Agent 版本、连接名称、服务管理方、已验证的提供商、项目路径及具体结果。记录待完成的登录／重启步骤，以及任何尚未测试的生命周期行为。仅安装好 WSL 软件包或健康请求成功，并不代表端到端配置已完成。

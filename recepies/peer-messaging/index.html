通过一个 WebSocket 连接两个 Happy Agent#

当桌面电脑或私有机器需要向可达的 Happy Agent 发起一条出站连接，再通过它双向交换消息时，使用本指南。桌面端不需要入站端口、公网地址或反向 URL。接口契约见 API_P2P.md。

取得两个安装实例的管理访问权限#

任一安装实例上的参谋长，都可以通过现有的已授权 SSH／部署访问权限，或现有的托管连接，协调两端设置。对等消息通信不会开放配置端点。使用托管连接时，通过普通 API 向远端参谋长发送已获授权的设置请求。

POST /v0/connections/<existing-connection>/api/v0/agents/<remote-chief-agent-id>/send

遵循主 API 的认证与发送契约。text 说明已获授权的设置内容，content 可以携带 tool_call_request，包含下文的确切工具及参数。通过同一管理路径观察远端执行情况。通过 SSH 部署时，写入对应的机器级 happy.toml 设置，并按正常流程重载配置。保留无关设置，先检查现有运行时覆盖项；绝不手动编辑自动生成的 runtime.toml。

选择稳定的节点 ID：本示例使用 desktop 和 server。服务器通过系统 Tailscale 或其他私有网络，在 100.80.0.20:24780 上可达。只需保证桌面端到服务器这个方向的网络可达。如果选择通过 TLS 终止代理传输，则使用 wss://。本功能不会配置 Tailscale 或内嵌 Tailcat 服务。

使用 Node 的 crypto 模块执行 randomBytes(32).toString("base64url")，生成一个私密的配对令牌。将其保存在内存或私有文件中，在两个安装实例上使用同一个值，不要让它出现在报告或命令输出中。不同的对等连接需要不同的令牌。下文的 <PAIR_TOKEN> 表示这个值。

先配置服务器，再配置仅出站的桌面端#

让服务器上处于活动状态的管理员参谋长调用 configure_peer_messaging。

{ "enabled": true, "node_id": "server", "listen": true, "host": "100.80.0.20", "port": 24780 }

然后调用 set_peer_connection。

{ "node_id": "desktop", "connection": { "role": "accept", "token": "<PAIR_TOKEN>" } }

这条接收配置中不应包含桌面端 URL。轮询 debug_peer_connections，直到服务器无错误地进入监听状态，并完成接收端对等连接配置。

在桌面端调用 configure_peer_messaging。

{ "enabled": true, "node_id": "desktop", "listen": false }

然后调用 set_peer_connection。

{
    "node_id": "server",
    "connection": { "role": "connect", "url": "ws://100.80.0.20:24780", "token": "<PAIR_TOKEN>" }
}

配置工具的确认响应表示配置意图已被持久化接纳。设定明确的截止时间，轮询调试信息，直到两端都报告 connected: true，且具有相同的会话 ID。桌面端必须报告 listenEnabled: false 和 listening: false。服务器必须为 role: "accept"，且没有反向 URL。连接或认证失败只会以安全的诊断信息形式呈现。

服务器上等效的机器级设置如下。

[peer_messaging]
enabled = true
node_id = "server"
listen = true
host = "100.80.0.20"
port = 24780

[peer_messaging.peers.desktop]
role = "accept"
token = "<PAIR_TOKEN>"

桌面端如下。

[peer_messaging]
enabled = true
node_id = "desktop"
listen = false

[peer_messaging.peers.server]
role = "connect"
url = "ws://100.80.0.20:24780"
token = "<PAIR_TOKEN>"

这些工具会持久化私有的自动生成运行时覆盖项，无需重启守护进程。项目设置不能配置对等连接。

验证实时健康状态与双向消息通信#

在桌面端调用 check_peer_connection，参数为 {"node_id":"server"}，在服务器上以 {"node_id":"desktop"} 调用同一工具。两端都必须报告可达、已认证且已就绪。这些检查通过现有会话的 ping/pong 完成；服务器不会反向连接桌面端。

遵循已部署节点的验证规则：分别通过两个安装实例各自独立认证的主 API，新建一次性项目和智能体，记录返回的 Agent ID，并将它们告知两个智能体。每条消息发送前都要确认项目仍处于活动状态。对等 API 不执行发现操作。

从桌面端的验证智能体调用 send_peer_agent_message。

{
    "node_id": "server",
    "to_agent_id": "<SERVER_TEST_AGENT_ID>",
    "text": "Peer setup probe. Reply through send_peer_agent_message to node desktop, Agent ID <DESKTOP_TEST_AGENT_ID>, saying: Peer round trip complete."
}

观察服务器智能体对话记录中的来源节点与来源智能体标识、服务器智能体发出回复时的工具调用，以及桌面端对话记录中收到的回复。确认调试信息仍显示两端使用相同会话 ID。发送成功的确认意味着消息已被持久化收件箱接纳；实际观察到回复，才能证明两个方向无需另建连接就能正常工作。

重连只恢复会话，绝不会重放消息。确认响应丢失可能意味着消息已经送达；检查接收方，并在确需重试时复用报告的消息 ID。如果两个临时项目仍处于活动状态，将其归档，并通过主 API 确认清理完成。报告实时健康状态、往返通信证据、桌面端仅出站状态及清理结果，不包含凭据。

诊断、轮换或断开连接#

绑定错误只与监听的服务器有关。主动连接端断开时，可能是节点 ID、令牌、端点、TLS／私有网络可达性或角色设置有误。两端角色必须互补。旧会话关闭前，重复会话会被拒绝；心跳用于检测半开连接。

在两个节点上通过 set_peer_connection 轮换配对令牌。旧会话会关闭，主动连接端使用新令牌重新连接。再次轮询调试信息并执行 ping。remove_peer_connection 撤销本地的该对等连接；断开一对节点时，两端都要配置。调用 configure_peer_messaging，参数为 {"enabled":false}，设置应用后会关闭本地会话并取消重连任务。链路不可用期间，本地智能体继续工作。

部署独立远程智能体#

当用户希望在另一台机器上部署个人、非团队模式的 Happy Agent，并能从现有 Happy 安装实例发起编程任务、尽量减少后续设置时，使用本指南。远端是独立的守护进程，拥有自己的项目、智能体、个人资料和凭据。此次部署不要创建 Happy 团队、WorkOS 组织或团队登录。

按需阅读配置和 Tailcat。准确的 API 请求以已安装版本的 API.md 为准（源码检出目录中位于 packages/happy-agent/API.md）。本指南面向使用 systemd 的全新 Linux 服务器；在 macOS 上应调整服务管理器与路径，而不是直接执行 Linux 命令。

默认自动执行#

智能体端到端执行本指南：核实目标机器与当前设置，将本地个人资料复制到远程配置，配置已获授权的凭据，安装并启动服务，登记连接，配置 Git，并执行完成检查。不要把示例变成留给用户完成的作业。复用已有选择与已授权访问，不要每一步都询问。只有缺少重要选择或授权时才提问；遇到无法避免的浏览器、设备登录、SSH 或钥匙串批准时暂停，随后自动继续。自动化绝不会绕过权限审查，也不意味着可以转移无关账号的凭据。

1. 确定少数关键选择#

复用用户已经提供的信息。将仍缺少的信息集中询问。

  • 使用哪台机器和哪个 SSH 账号？确认其主机密钥、操作系统、架构，以及安装持久服务和启用远程访问的权限。
  • 远端应使用哪些提供商账号？说明复制凭据会让该机器获得这些账号的访问权，并能使用其消费额度。取得对具体凭据和目标机器的同意；尽可能优先在远端重新登录或使用专用凭据。
  • “是否也要在那里设置 GitHub？我可以安装 GitHub CLI（gh），登录你选择的 GitHub 账号，并配置 Git 使用它。”确认 GitHub 主机、账号和仓库。
  • 在计划使用的本地仓库中，读取当前用户实际生效的 git config --get user.name 和 git config --get user.email；没有仓库时读取全局值。向用户建议在远端使用这些完全相同的值：“远端也将使用这个 Git 名称和邮箱；需要改成别的吗？”缺失或有歧义时再询问。如果用户使用 GitHub no-reply 邮箱，就保留它；绝不根据用户名编造邮箱。
  • 复用请求或本地设置中的远端友好名称、默认提供商／模型，以及初始仓库或工作文件夹。只有缺失或有歧义时才询问。
  • 作为本地安装实例上处于活动状态的管理机器人，调用 get_local_profile，参数为 {}。它直接从本地存储读取已有名称和邮箱，不发起 API 请求。默认复用这些值，并与 Git 提交身份分开处理。只有值缺失（null）或用户要求不同的远端个人资料时才询问。绝不将个人资料数据库、私有身份、安装 ID 或版本复制到远端。

如果已有安装实例，先检查其服务、账号、配置和项目。保留现有内容，只合并用户要求的设置。不要为了套用这些全新安装示例而替换现有守护进程的身份、凭据或数据。

exe.dev 部署说明#

如果用户现有的 ~/.ssh/id_ed25519 密钥已获 exe.dev 授权，优先使用它进行 SSH 连接。使用 exe.dev 返回的 VM 地址和登录用户；不要编造 SSH 主机名，也不要把私钥复制到 VM。验证主机密钥，并显式指定密钥，例如 ssh -i ~/.ssh/id_ed25519 <confirmed-user>@<confirmed-vm-host>。

exe.dev 默认的 bearer 令牌可以创建和列出 VM，但不能进行 SSH 连接、删除 VM 或添加 SSH 密钥。因此，成功创建 VM 不能证明已经具备初始化访问权限。如果 SSH 未获授权，请用户安排所需访问；不要用该令牌重试特权操作，也不要将其当作 Happy Agent 凭据。

SSH 可用时，避免使用 exe.dev 首次启动脚本。它们只执行一次，运行身份是 exedev，而不是 happy-agent 服务用户；在 HTTPS 请求体中引用换行也容易出错。应改用经过检查、可重复执行的 SSH 步骤。标准 x86-64 exe.dev VM 使用 linux-x64 压缩包，但仍需先检查 uname -m。使用下文服务用户实际的 Linux happy/config 目录，而不是照搬旧部署的路径。

2. 安装二进制并准备一个服务账号#

使用专用的非特权账号，本例为 happy-agent，主目录为 /var/lib/happy-agent。守护进程、提供商凭据、Git 配置、GitHub 登录和仓库都必须属于该账号，而不是 root 或 SSH 操作者。在全新的 Debian／Ubuntu 主机上执行以下操作。

sudo apt-get update
sudo apt-get install -y ca-certificates curl git jq tar
sudo useradd --system --create-home --home-dir /var/lib/happy-agent \
  --shell /bin/bash happy-agent
sudo chmod 0700 /var/lib/happy-agent
sudo install -d -m 0700 -o happy-agent -g happy-agent \
  /var/lib/happy-agent/happy/config \
  /var/lib/happy-agent/.happy \
  /var/lib/happy-agent/.config/happy-agent/credentials \
  /var/lib/happy-agent/projects

如果此节点自行运行智能体工作，而不是使用专用执行器，也应提出通过独立 Linux 用户加固的选项：这样，智能体命令会以工作负载用户运行，无法读取此账号的配置、数据库或凭据。在守护进程首次启动前作出决定，因为该指南会把所有项目和工作区文件夹放入工作负载用户的主目录，并将二进制安装为 /usr/local/bin 下由 root 所有的文件。

除非用户固定了版本，否则在部署时从 GitHub 查找最新稳定版 Happy Agent。筛选 Happy Agent 的 v<version> 标签，而不是库的发布版本；不要复用先前部署时记住的版本。根据 uname -m 匹配 linux-x64 或 linux-arm64。在全新的临时目录中下载，验证已发布的校验和，然后安装。

set -eu
DEPLOY_DOWNLOAD_DIR="$(mktemp -d)"
cd "$DEPLOY_DOWNLOAD_DIR"
DEPLOY_TAG="$(curl -fsSL 'https://api.github.com/repos/slopus/happy-agent/releases?per_page=100' |
  jq -er '[.[] | select(.draft == false and .prerelease == false) |
    select(.tag_name | test("^v[0-9]+\\.[0-9]+\\.[0-9]+$"))][0].tag_name // error("No stable Happy Agent release found")')"
DEPLOY_VERSION="${DEPLOY_TAG#v}"
case "$(uname -m)" in
  x86_64) DEPLOY_TARGET="linux-x64" ;;
  aarch64|arm64) DEPLOY_TARGET="linux-arm64" ;;
  *) echo "Unsupported Linux architecture; choose a supported release target." >&2; exit 1 ;;
esac
DEPLOY_ARCHIVE="happy-agent-$DEPLOY_VERSION-$DEPLOY_TARGET.tar.gz"
DEPLOY_RELEASE_URL="https://github.com/slopus/happy-agent/releases/download/v$DEPLOY_VERSION"
curl -fLO "$DEPLOY_RELEASE_URL/$DEPLOY_ARCHIVE"
curl -fLO "$DEPLOY_RELEASE_URL/$DEPLOY_ARCHIVE.sha256"
sha256sum --check "$DEPLOY_ARCHIVE.sha256"
tar -xzf "$DEPLOY_ARCHIVE"
sudo install -m 0755 "happy-agent-$DEPLOY_TARGET" /usr/local/bin/happy-agent
/usr/local/bin/happy-agent --version

下载或校验和验证失败时停止。发布二进制是自包含的，并内嵌 Tailcat 服务器；无需源码检出目录、Node.js 或单独安装 Tailcat 服务器。只在初始项目需要时安装仓库专用的运行时／包管理器。macOS 使用匹配的 darwin-* 产物、shasum -a 256 -c、所选用户的 ~/Happy/Config/happy.toml，以及该用户下的持久 launchd 服务。

如果 GitHub 查询受到速率限制，或当前页没有 Happy Agent 发布版本，应继续查询剩余页面，或通过已授权的 GitHub 客户端查找版本；不要猜测版本号。记录选定版本以便交接。首次启动前，确认 /var/lib/happy-agent/.happy 属于 happy-agent，尤其是在之前以 root 身份初始化并创建过该目录的情况下。对现有安装，应先检查所有权，再做限定范围的修复；绝不递归修改无关目录或跟随未经验证的符号链接。

Ubuntu 命名空间权限#

在 Ubuntu 24.04 上首次启动前，检查主机的 AppArmor 命名空间限制，并遵循 Ubuntu AppArmor 主机前置要求。为可信且由 root 所有的守护进程可执行文件授予应用专属 userns 权限前，需取得批准。保留现有约束配置；不要关闭系统范围的限制、授予服务 capabilities，或把 Auto 改为 Full access。如果此主机策略变更未获授权，应报告沙箱启动受阻，而不是声称部署已完成。

3. 只配置选定提供商的凭据#

绝不打印认证文件或令牌、将它们粘贴到聊天中、放入命令参数或 Git，也不要在处理时开启 shell 跟踪。使用现有且经过审查的密钥机制，或直接通过加密 SSH／SCP 传输。如果缺少授权或安全访问方式，让用户私下完成该步骤。不要绕过钥匙串或权限限制。

传输文件时，在目标机器上用 mktemp -d 创建私有暂存目录，使用它返回的确切路径，通过 scp 传输已获授权的本地认证文件，然后将文件安装为服务账号所有。例如，传输到私有暂存路径后执行以下操作。

sudo install -m 0600 -o happy-agent -g happy-agent \
  /EXACT_PRIVATE_STAGING_PATH/auth.json \
  /var/lib/happy-agent/.config/happy-agent/credentials/codex.json

对每个选定厂商替换暂存路径和目标路径。验证已安装文件后，只删除确切的暂存凭据副本。凭据文件和配置的权限必须为 0600，私有父目录为 0700。Codex 和 Grok 会原地刷新凭据，因此文件及其父目录都必须允许服务账号写入。不要复制整个主目录或无关账号。重复的 OAuth 会话可能因刷新令牌轮换而相互干扰；如果复制导致任一机器不稳定，应在远端单独登录。

将下文的提供商配置段写入远程机器的 /var/lib/happy-agent/happy/config/happy.toml。使用远端绝对路径，而不是源机器的路径。含有 REPLACE_... 的示例是模板，不是可用凭据。通过私有编辑器／密钥配置工具填入秘密值，不要使用模型可见的补丁或 shell 命令字面量。不要假定 TOML 会展开字符串中的环境变量。

OpenAI / Codex#

通过官方 CLI 执行 codex login 登录。通常文件为 ~/.codex/auth.json，或名为 auth.json、位于用户配置的 CODEX_HOME 目录中的文件。将完整文件（包括会话／刷新数据及账号身份）复制到远程凭据路径。不要只提取访问令牌。仅存于钥匙串的登录不是可移植文件：请使用 Codex 支持的基于文件的登录方式，或在远端登录；绝不复制操作系统钥匙串。查看已安装 Codex CLI 的帮助，确认其支持的登录流程。

[providers.codex]
enabled = true
auth_file = "/var/lib/happy-agent/.config/happy-agent/credentials/codex.json"
transport = "auto"

如果用户选择 OpenAI API 密钥而不是 Codex 订阅登录，在此配置段中使用 api_key，私下填入值，并省略 auth_file。API 计费和可用模型可能不同。不要悄悄将订阅认证改成付费 API 密钥。

Anthropic / Claude Code#

对于无界面的远端，优先使用已授权账号现有的长期 setup token。否则，智能体可以按下文说明自动提取当前钥匙串令牌，但需注意所述有效期限制。需要新的长期令牌时，以计划使用的已登录用户运行 claude setup-token，只在私密登录交互时请用户参与。私下传输生成的令牌，并写入远程配置。

[providers.claude]
enabled = true
oauth_token = "REPLACE_WITH_PRIVATE_SETUP_TOKEN"

或者，如果源机器使用基于文件的 Claude 登录，将 ~/.claude/.credentials.json（或 CLAUDE_CONFIG_DIR 中的对应文件）复制到远端私有目录，文件名保持为 .credentials.json。配置的是目录而不是文件，并省略 oauth_token。

[providers.claude]
enabled = true
config_dir = "/var/lib/happy-agent/.config/happy-agent/credentials/claude"

直接读取已有的 macOS 钥匙串令牌

Claude 通常将 OAuth 凭据保存在登录钥匙串中；仅复制 ~/.claude 不会复制该登录。获得将此账号转移到所选远端的授权后，智能体可以自动提取当前令牌。以本地已登录用户运行，而不是 root。如果 shell 沙箱无法访问钥匙串，使用经过审查的主机访问方式；绝不绕过拒绝。任何 macOS 批准提示都应由用户处理。

对于默认 Claude 配置，以下 Bash 片段读取 Claude Code-credentials 通用密码条目，只将 claudeAiOauth.accessToken 提取到私有文件。它特意不打印 JSON 凭据或令牌。

set -euo pipefail
umask 077
CLAUDE_TOKEN_DIR="$(mktemp -d)"
/usr/bin/security find-generic-password \
  -a "$(id -un)" -s "Claude Code-credentials" -w |
  jq -er '.claudeAiOauth.accessToken | select(type == "string" and length > 0)' \
  > "$CLAUDE_TOKEN_DIR/oauth-token"
test -s "$CLAUDE_TOKEN_DIR/oauth-token"

不要单独运行 security ... -w 命令、使用 shell 跟踪，或将该文件读入工具输出。查找或提取失败时停止。保留确切的临时路径用于加密传输，然后使用理解 TOML 的配置工具，私下将文件内容载入远端的 [providers.claude] oauth_token。此设置接受令牌值，而不是文件路径。不要将秘密值放入命令参数或模型可见的补丁。验证认证成功后，只删除两台机器上确切的暂存令牌文件。

对于自定义 Claude 环境，应选择其实际的钥匙串条目，而不是猜测账号：设置了 CLAUDE_CONFIG_DIR 时，在服务名末尾添加 -，再加上实际目录字符串 SHA-256 值的前八个小写十六进制字符。设置了 CLAUDE_CODE_CUSTOM_OAUTH_URL 时，将 -custom-oauth 插入 Claude Code 之后。最终服务名为 Claude Code[-custom-oauth]-credentials[-<directory-hash>]。使用拥有该登录的账号；通常账号就是本地用户名。这些规则与 Happy 查找 Claude 凭据的方式一致。

这只是当前的访问令牌，不是新签发的长期 setup token。Happy 的静态 oauth_token 设置不会从本地 Mac 刷新它，复制 .credentials.json 也不会让 Happy 获得 Claude 刷新流程。如果存在 claudeAiOauth.expiresAt，私下检查有效期；此刻验证成功并不保证之后能无人值守运行。要长期无人值守使用，优先采用已有的长期 setup token，或在需要续期时安排 claude setup-token／远端重新登录。所有非交互工作都应自动完成，只为登录交互本身请求用户参与。交接时说明续期要求；这两类令牌都不是永久有效，也都可能被撤销。

如果用户选择 Anthropic API 密钥，则改用 api_key，同样私下处理，并明确取得计费同意。选择一种认证方式，不要设置多个相互竞争的覆盖项。

xAI / Grok#

通过官方 CLI 为计划使用的账号运行 grok login。将完整的 ~/.grok/auth.json，或自定义主目录下的 $GROK_HOME/auth.json（如已配置），安全复制到远端。完整保留所有作用域记录和刷新元数据。

[providers.grok]
enabled = true
auth_file = "/var/lib/happy-agent/.config/happy-agent/credentials/grok.json"

Grok 会刷新会话并原子重写此文件。如果用户明确选择 xAI API 密钥，使用 api_key 代替 auth_file；验证目标模型能通过该密钥使用。

Amazon Bedrock#

主机运行在 AWS 上时，优先使用最小权限的实例／任务角色，这样就不需要复制本地密钥。否则，选择 Bedrock bearer 密钥或受支持的 AWS 凭据链。使用 bearer 密钥时，私下填入以下配置。

[providers.bedrock]
enabled = true
region = "us-east-1"
bearer_token = "REPLACE_WITH_PRIVATE_BEDROCK_KEY"

也可以使用 bearer_token_env_var = "AWS_BEARER_TOKEN_BEDROCK"，并在第 5 步将值写入服务的私有环境文件；省略 bearer_token。SSH 会话中的 export 不会被 systemd 继承。

使用 AWS profile 时，只从 ~/.aws/config 和 ~/.aws/credentials 传输已获授权 profile 的设置和凭据，保留 AWS 格式。将它们安装为私有文件，并显式选择。

[providers.bedrock]
enabled = true
region = "us-east-1"
profile = "remote-bedrock"
config_file = "/var/lib/happy-agent/.config/happy-agent/credentials/aws-config"
credentials_file = "/var/lib/happy-agent/.config/happy-agent/credentials/aws-credentials"

配置段为 [profile remote-bedrock]，凭据段为 [remote-bedrock]。临时凭据还需要对应的会话令牌。复制即将过期的凭据或 SSO 缓存，不是持久认证方式：应在远端完成受支持的 AWS 登录，或以服务用户安装并配置其 credential_process 辅助程序。确保辅助程序可以非交互执行，并能在那里刷新凭据。选择账号实际可用的区域和模型。

可选的 Gemini 工具#

如果用户需要 Gemini 媒体／搜索工具，将其选定密钥私下复制到 [gemini] api_key，或在守护进程环境文件中设置 GEMINI_API_KEY。Gemini 不是聊天提供商配置项。不要仅仅因为本地存在额外凭据，就把它们一并复制。

4. 完成远程配置#

在远端 happy.toml 中，将以下设置与选定提供商的配置段合并。

[providers]
default_enable = false

[profile]
name = "REPLACE_WITH_LOCAL_PROFILE_NAME"
email = "REPLACE_WITH_LOCAL_PROFILE_EMAIL"

[feature.team]
enabled = false

[api]
token = "REPLACE_WITH_FRESH_43_CHARACTER_BASE64URL_TOKEN"

[feature.tailcat]
enabled = true
port = 24779

[defaults]
provider = "codex"
model = "REPLACE_WITH_AVAILABLE_MODEL_ID"
permission_mode = "auto"

将默认提供商和模型替换为用户选择的可用组合。只启用已经配置了认证的提供商。Auto 会审查操作；绝不要仅为通过初始化检查而选择 Full access。合并片段时，每个 TOML 表只能出现一次。

将两个 [profile] 字段从 get_local_profile 的返回值写入这个全局配置，务必在首次启动前完成，并使用 TOML 序列化器进行转义。启动时会创建远端自己的个人资料，并从这些记录中补齐缺少的名称／邮箱字段。这能满足初始引导中的个人资料要求，无需显示资料创建界面，也无需通过 HTTP 修改个人资料。不存在 skip_profile 标志：不要用空资料绕过要求。其他初始检查仍然适用，包括提供商凭据和项目。后续对个人资料的编辑在重启后会保留；配置只补齐仍然缺失的字段。项目配置不能设置这些值，团队部署则会拒绝共享的 [profile] 段。使用支持这些设置的版本；如果选定的旧版不支持，应报告需要升级，而不是悄悄回退到调用个人资料 API。

全新远程部署时，安全生成 32 个随机字节，以不带填充的 43 位 base64url 字符编码，并将此新值私下写入 [api] token。这样，远端及其主连接从一开始就拥有一个明确的凭据。绝不复用 exe.dev 令牌、提供商凭据或另一安装实例的令牌。升级时保留已有安装实例的令牌。不显式设置时，守护进程可以自行生成令牌，但本部署指南特意预先配置一个，并使用完全相同的值登记连接。

Tailcat 提供无需账号的加密连接，而不是身份认证。任何获知其地址的人都能接触到 API 认证边界；bearer 令牌授予独立守护进程的访问权。两者都应保密，启用这种对外可达能力前应取得同意。不需要公开的未认证 HTTP 监听端点、WorkOS 配置或 Tailscale 账号。

5. 安装可可靠重启的服务#

安装 /etc/systemd/system/happy-agent.service。

[Unit]
Description=Happy Agent (standalone)
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=happy-agent
Group=happy-agent
WorkingDirectory=/var/lib/happy-agent
Environment=HOME=/var/lib/happy-agent
EnvironmentFile=-/var/lib/happy-agent/.config/happy-agent/service.env
ExecStart=/usr/local/bin/happy-agent run
Restart=on-failure
RestartSec=2
UMask=0077

[Install]
WantedBy=multi-user.target

如果任何凭据使用环境变量，私下创建 service.env，采用 NAME=value 条目，不加 export，并使用正确的 systemd 引号规则。所有者设为 happy-agent，权限设为 0600；不要把秘密值放进所有人可读的 unit 文件。使用显式路径，将必需的凭据辅助程序／运行时加入服务的 PATH。避免另一安装实例遗留的提供商变量造成竞争。

sudo chown happy-agent:happy-agent /var/lib/happy-agent/happy/config/happy.toml
sudo chmod 0600 /var/lib/happy-agent/happy/config/happy.toml
sudo systemctl daemon-reload
sudo systemctl enable --now happy-agent
sudo systemctl is-active happy-agent

设置明确的等待截止时间，等待经过认证的 /v0/health 报告就绪，而不只是确认进程存在。默认本地套接字为 /var/lib/happy-agent/.happy/agent/server.sock；令牌文件为 /var/lib/happy-agent/.happy/agent/token。使用受保护的客户端／请求头文件或客户端 SDK，确保令牌绝不会出现在进程参数或工具输出中。失败时，查看长度受限且已脱敏的日志片段；不要倾倒含凭据的配置。保持 systemd 为服务管理者，不要再用 happy-agent start 启动第二个守护进程。

部署后的平稳维护#

升级或计划停机维护时，使用独立的 SSH／操作会话，不要使用由即将停止的守护进程所拥有的工具。

sudo -u happy-agent -H /usr/local/bin/happy-agent drain &&
sudo systemctl stop happy-agent

在支持基于信号排空工作的版本中，第一条命令使用 SIGUSR2 和私有本地状态，不需要 API、提供商或 WorkOS 令牌。它会等待已接纳的智能体工作到达安全且可持久化的边界，再报告完成，同时让守护进程继续运行在只读排空模式。新工作会被拒绝，待处理工作保持持久化。重复执行 drain 是安全的。如果命令失败，应停止并检查原因，不要继续维护。

第二条命令通过 SIGTERM 请求平稳关闭。在守护进程退出前，具名清理处理器会关闭运行时的服务和进程、数据库连接及 API 传输通道。等待其退出后，再备份或替换文件。单独发送 SIGTERM 不会先排空正在进行的推理。排空操作也不会等待任意终端／后台任务完成，因此需要另外安排；强制终止不属于平稳关闭。

happy-agent drain 会检查运行中守护进程的信号支持情况和进程身份。不要向旧版本直接发送 SIGUSR2，这可能终止进程。保持相同的服务用户及任何 HAPPY_HOME_DIR 覆盖设置。直接使用信号、处理旧版本、备份、关闭进度和恢复等内容，参见升级指南。

强烈建议：使用专用执行器#

节点健康后，建议添加专用执行器，并在用户同意后实施：第二台机器运行智能体命令、Git、终端和项目文件夹，此节点则保留数据库、提供商凭据和令牌。在第 7 步登记初始项目前完成，这样项目从一开始就克隆在执行器上；执行器主动连接此节点的 Tailcat 端点，因此无需入站端口。

6. 连接主安装实例#

最多等待 90 秒，让远端私有的 .happy/agent/tailcat/address 和 tailcat/port 文件出现。两者必须都存在，且服务保持健康。将地址、端口和守护进程令牌安全传输到主机器。绝不复制 Tailcat 私有身份密钥。

在主安装实例上，让活动中的参谋长／管理机器人通过 set_remote_connection 登记这些确切值。输入结构如下。

{
    "id": "personal-server",
    "connection": {
        "name": "Personal server",
        "address": "REPLACE_WITH_EXACT_TAILCAT_ADDRESS",
        "port": 24779,
        "token": "REPLACE_WITH_REMOTE_API_TOKEN"
    }
}

令牌应通过已批准的私有凭据配置路径传入；绝不在聊天、日志或交接中重复它。该工具登记已有远端，不负责部署 VM。它会写入主安装实例自动生成的运行时配置，无需重启主实例即可生效。然后调用 check_remote_connection_health，参数为 { "id": "personal-server" }，并要求 reachable、authenticated 和 ready 全部为 true。这是独立的检查：可达端点可能拒绝认证，已认证的守护进程也可能仍在启动。这证明了连接可用，但不证明提供商推理可用；第 8 步还需单独验证提供商凭据。

如果没有活动的管理机器人或安全的工具凭据传入路径，手动替代方案是编辑主机器的全局 happy.toml（不是远端的，也不是仓库内的文件）。

[connections.personal-server]
name = "Personal server"
address = "REPLACE_WITH_EXACT_TAILCAT_ADDRESS"
port = 24779
token = "REPLACE_WITH_REMOTE_DAEMON_TOKEN"

使用区分大小写的确切地址数据，而不是 tailcat:// URL，并使用实际配置的端口。选择尚未使用的连接 ID，并将配置文件限制为仅所有者可访问。不要在独立连接中添加 workos_organization_id。协调正在进行的工作后，重启主守护进程以应用文件变更。动态连接覆盖项保存在自动生成的 runtime.toml 中，优先级高于全局条目；应处理已有覆盖项，而不是追加相互竞争的设置。

通过主实例经过认证的 API 验证：GET /v0/connections 应列出远端，GET /v0/connections/personal-server/api/v0/health 应能到达远端并报告就绪。主凭据用于向主实例认证；它的连接层负责提供远端令牌。内置传输机制可处理此连接，无需单独的客户端登录。手动 Tailcat 客户端需要其自身的 v0.7.0 可执行文件；参见 Tailcat。

如果健康检查返回 401，检查远端令牌；如果不可用，检查 Tailcat 状态、出站连接和确切地址／端口。不要为排障而关闭认证。升级时保留远端的 .happy/agent 状态，以保全数据、令牌和 Tailcat 身份。

7. 设置 Git 身份，并按需配置 GitHub 认证#

无论用户是否拒绝 GitHub 设置，都必须为服务用户设置约定的 Git 身份。

sudo -u happy-agent -H git config --global user.name "CONFIRMED_NAME"
sudo -u happy-agent -H git config --global user.email "CONFIRMED_EMAIL"

如果用户接受 GitHub 设置，按 GitHub CLI 官方说明或通过可信发行版软件包安装 gh（Debian／Ubuntu 上可用时执行 sudo apt-get install -y gh），然后验证 gh --version。以 happy-agent 而不是 root 进行认证。

sudo -u happy-agent -H gh auth login --hostname github.com --git-protocol https --web
sudo -u happy-agent -H gh auth setup-git --hostname github.com
sudo -u happy-agent -H gh api user --jq .login

无界面登录时，用户在自己的机器上完成浏览器／设备步骤。适用时，改用用户已确认的 GitHub Enterprise 主机。只申请所选仓库必需的访问权限，包括必要的组织 SSO 授权。没有密钥环时，gh 可能将令牌保存在 ~/.config/gh/hosts.yml；应放在私有目录中，并仅允许所有者访问。

如果用户明确希望复制现有 GitHub 令牌，以服务用户身份通过 stdin 私下将其传入 gh auth login --hostname github.com --git-protocol https --with-token，然后运行 gh auth setup-git。绝不让 gh auth token 出现在模型可见输出中，不把令牌放进 Git URL，也不复制无关 GitHub 账号。范围较窄的令牌可能不支持所有 gh 操作；应验证必需操作。仅设置 GH_TOKEN 不能证明持久的 Git 凭据辅助程序已配置完成。测试时不要依赖 SSH 操作者的环境。

以服务用户通过 HTTPS 将约定的仓库克隆到 /var/lib/happy-agent/projects；如果未要求仓库，则创建约定的本地工作文件夹。通过 Happy 或文档中的项目 API，将其登记为远端项目。使用执行器时，改为通过远端项目 API 在执行器上克隆或登记；下述 Git 身份检查也应以执行器的服务用户运行。在该仓库中检查以下事项。

  • git config --get user.name 和 git config --get user.email 与约定身份一致；
  • git var GIT_AUTHOR_IDENT 正确解析；
  • 如果配置了远程仓库，git ls-remote origin 能非交互执行；
  • GitHub 账号和仓库权限符合用户要求。

现有仓库级身份覆盖项优先于全局值；修改有意设置的覆盖项前应询问。Git 作者身份与 GitHub 认证是两回事。读取测试不能证明写入权限；应检查已授予的仓库权限，并说明哪些尚未测试。未经明确授权，不要推送测试提交。如果用户拒绝 GitHub 设置，不要安装其 CLI 或复制其凭据；说明由此带来的私有仓库访问限制。

8. 证明已就绪并完成交接#

通过用户实际使用的连接，对远端执行检查。

  1. 使用 POST /v0/providers/:providerId/verify 和 { "level": "inference" } 验证每个选定提供商。这些检查可能产生少量提供商费用。必须得到 status: "passed"；仅有 HTTP 200 不够，因为验证失败时也可能返回 200。通过 GET /v0/config 查看远端模型目录，确认默认提供商／模型存在。
  2. 确认由配置初始化的远端个人资料具有预期的名称和邮箱，且无需手动创建资料。远端管理机器人可使用 get_local_profile 检查。不要通过个人资料 API 写入。验证初始项目已经登记，且初始引导报告其实际前置条件均已满足；不要为了掩盖缺失步骤而把未完成的设置标记为完成。
  3. 遵循测试已部署的节点：在远端新建临时项目，使用独立的一次性工作区和智能体，与初始项目分离。绝不复用现有项目进行测试。通过 Happy 发送一个小任务，检查工作目录、运行无害的 shell 命令，并在临时工作区内创建／读取一次性文件。确认模型推理、工具执行、存储写入和用户可见响应均正常。测试用户期望使用的每一家提供商。每个测试动作前，检查用户是否已归档临时项目；如果已归档，停止，不恢复或替换它。
  4. 没有活动工作时，重启远程服务。确认 systemd 已启用，经过认证的健康检查恢复，Tailcat 端点未变化，且主实例重新连接。向测试智能体发送后续任务前，再次检查临时项目的归档状态；如果用户已经归档，就停止。只读检查初始项目保留的状态。如果启用了 GitHub，以服务用户重新检查非交互 Git 访问。重启整台机器的测试需要用户批准。
  5. 验证后将临时项目归档，即使检查失败也一样，并确认其归档状态。如果用户已归档，保持归档。报告未完成的检查或清理；不要归档初始项目或其他已有项目。

提供简洁交接：机器与连接名称、已安装版本、服务／配置／项目位置、已验证的提供商及默认模型、个人资料与 Git 身份、GitHub 账号／设置选择，以及通过了哪些检查。提供维护用的 sudo systemctl status happy-agent 和 sudo systemctl restart happy-agent，并说明凭据有效期／续期步骤。绝不包含令牌或认证文件内容。明确报告待用户完成的登录步骤或尚未验证的访问权限；仅仅能连接到守护进程，不代表智能体已经全面可用。

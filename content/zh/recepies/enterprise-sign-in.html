设置企业 JWT 登录#

当组织希望成员使用组织自己的身份提供商（Okta、Entra ID、Google Workspace、Keycloak、内部 SSO 等），而不是 Happy 的 WorkOS 账号，登录团队模式 Happy Agent 时，使用本操作指南。最终得到的是一个验证组织签发的 JWT 访问令牌的团队模式守护进程，以及一个由组织拥有、供 Happy 桌面或移动应用直接登录的 OAuth 授权服务器。

请先阅读团队部署模式；其中关于安装、Tailcat、首次设置和验证的所有说明仍然适用。本指南只替换其中的 WorkOS 认证方式。它不授权修改组织的身份提供商、在其中注册应用，或将服务发布到互联网；请向用户所在组织的管理员申请相应权限。

此功能要求 Happy Agent 发布版包含企业 JWT 认证。客户端通过 GET /v0/authentication 检测支持情况；旧版守护进程会返回 404。

登录如何工作#

这与 Slack 及其他桌面应用使用企业 SSO 的方式相同：应用通过系统浏览器将用户带到组织的登录页面，取得短时有效的一次性授权码，再自行用该授权码换取令牌。

守护进程被视为不可信任其接触凭据。它告诉应用在哪里登录，并验证应用发送来的访问令牌，但绝不会看到登录授权码、PKCE 秘密或刷新令牌。

Happy app                 Happy Agent daemon           Authorization server (deployer)
   |  GET /v0/authentication  |                                  |
   |------------------------->|                                  |
   |  oauth: authorizationUrl, tokenUrl, refreshUrl, clientId    |
   |<-------------------------|                                  |
   |  system browser: authorizationUrl?client_id&redirect_uri&state&code_challenge
   |------------------------------------------------------------>|  SSO login with the
   |                          |                                  |  identity provider
   |  browser redirects to redirect_uri?code=...&state=...       |
   |<------------------------------------------------------------|
   |  POST tokenUrl  code + code_verifier                        |
   |------------------------------------------------------------>|
   |  access_token (JWT), expires_in, refresh_token?             |
   |<------------------------------------------------------------|
   |  Authorization: Bearer <access_token>                       |
   |------------------------->|  verify signature, iss, aud, exp; read user ID
   |          ... later, when the access token expires ...       |
   |  POST refreshUrl  refresh_token                             |
   |------------------------------------------------------------>|
   |  new access_token (and maybe a new refresh_token)           |
   |<------------------------------------------------------------|
  1. Happy 应用询问守护进程如何登录。守护进程返回的任何 401 都携带相同的回答，因此应用可以从任意被拒绝的请求发起登录。
  2. 守护进程返回一种 oauth 方式：直接取自配置的授权端点、令牌端点、可选刷新端点、客户端 ID，以及可选的权限范围。
  3. 应用创建随机的 state 和 PKCE 校验值，将二者保存在内存中，并在系统浏览器中打开授权端点，绝不使用内嵌 Web 视图。应用会显示授权服务器的主机名，让用户看清自己正在何处登录。
  4. 授权服务器通过身份提供商完成用户登录，然后重定向到应用的 redirect_uri，并携带一次性授权码和 state。桌面端的重定向 URI 是类似 http://127.0.0.1:53682/callback 的回环地址；移动端则是应用自己的 URL 协议。
  5. 应用检查 state，然后在令牌端点提交授权码及 PKCE 校验值，换取令牌。即使有人截获重定向，也只会得到一个没有校验值就毫无用处、且数秒内就会失效的授权码。
  6. 应用在每次请求时将访问令牌发送给守护进程。它可以只将所有令牌保存在内存中。
  7. 访问令牌到期前或到期时，如果配置了刷新端点，应用会向该端点发送刷新令牌，取得新的访问令牌。没有刷新端点或刷新失败时，应用会再次通过浏览器登录。只要身份提供商自身的会话仍然有效，这个过程通常会立即完成，所以应用即使只在内存中保存凭据，也很少需要提示用户操作。

应用只会把刷新令牌发送到登录时记录的刷新端点，绝不会发送到守护进程后来公布的其他端点。客户端代码使用 @slopus/happy-agent-client 中的 beginOAuthSignIn、completeOAuthSignIn 和 refreshOAuthCredential；HappyAgentClient 接受令牌函数，因此刷新后的令牌无需重新创建客户端即可生效。

1. 选择授权服务器#

部署方需要一个支持公共客户端带 PKCE 的授权码流程，并签发 JWT 访问令牌的 OAuth 2.0 授权服务器。有两种方式：

  • 直接使用身份提供商。Okta、Entra ID、Auth0、Keycloak、Ping 及大多数现代身份提供商都开箱即用地支持此功能。注册一个原生或公共应用，允许 Happy 应用的重定向 URI，为这次部署定义 API 或资源，使访问令牌包含其受众；如有需要，启用刷新令牌。无需编写自定义代码。
  • 编写一个小型授权服务器，放在无法签发合适访问令牌的身份提供商之前，例如仅支持 SAML 的提供商。参见第 3 步。

2. 明确令牌契约#

  • 签发者（iss）：授权服务器的签发者，例如 https://sso.acme.example。
  • 受众（aud）：本次部署独有的值，例如 https://happy.acme.example。守护进程能看到发送给它的每个令牌；使用唯一受众可以阻止它将成员令牌重放给其他服务或另一套 Happy 部署。
  • 用户 ID 声明：稳定且永不重复使用的用户 ID。默认为 sub。优先使用不可变的对象 ID，而非邮箱地址。值应为 1–256 个可打印字符。
  • 所有者：应成为此部署所有者的用户 ID。
  • 客户端 ID 及可选权限范围：使用授权服务器为 Happy 应用注册的值。如果刷新令牌需要，请请求 offline_access 或提供商对应的权限范围。
  • 有效期：访问令牌应短时有效，通常为 5–60 分钟；如果组织希望保持较长会话，则配合刷新令牌使用。服务器支持时，应在每次使用后轮换刷新令牌。
  • 签名密钥：优先选择通过 JWKS URL 发布的非对称密钥，所有身份提供商都支持这种方式。支持的算法：RS256、RS384、RS512、PS256、PS384、PS512、ES256、ES384、ES512、EdDSA。也支持共享秘密（HS256、HS384、HS512，至少 32 字节），但任何持有它的人都能签发令牌，包括守护进程自身。当守护进程并非完全可信时，绝不要使用共享秘密，也绝不要在不同部署间共用一个秘密。

每个访问令牌都必须携带 iss、aud、exp 和用户 ID 声明。若有 nbf 和 iat，也会检查。时钟最多允许相差 30 秒。

3. 如果自行编写授权服务器#

按照 RFC 6749、RFC 7636 和 RFC 8252 实现三个端点。任何 OAuth 服务器库都可以做到；关键要求如下：

GET /oauth/authorize 接收 response_type=code、client_id、redirect_uri、state、code_challenge、code_challenge_method=S256，以及可选的 scope。

  1. 检查 client_id，并将 redirect_uri 与 Happy 应用回调的允许列表精确比对，例如 happy://auth/callback 和 http://127.0.0.1:<any port>/callback。绝不重定向到其他位置，即使是为了报告错误也不行。
  2. 通过身份提供商完成用户登录，并检查该用户是否被允许使用 Happy。
  3. 创建一个随机、一次性、约一分钟内过期的授权码，并将它与用户、client_id、redirect_uri 和 code_challenge 一起存储。
  4. 重定向到 redirect_uri?code=<code>&state=<state>，原样复制 state。

POST /oauth/token 接收表单，包含 grant_type=authorization_code、code、redirect_uri、client_id 和 code_verifier。消费该授权码，检查 client_id 与 redirect_uri 是否匹配，并检查 code_verifier 的 SHA-256 值经过 base64url 编码后是否等于已存储的挑战值。返回 JSON：

{
    "access_token": "<JWT>",
    "token_type": "Bearer",
    "expires_in": 900,
    "refresh_token": "<opaque random string>"
}

错误使用 400，并返回 { "error": "invalid_grant" } 或其他 OAuth 错误码。

POST /oauth/refresh（可选；也可以使用令牌端点）接收 grant_type=refresh_token、refresh_token 和 client_id，响应方式相同。刷新令牌应哈希后存储，每次使用时轮换，人员离开时撤销；若已轮换的令牌被重复使用，应视为被盗，并撤销整个会话。刷新端点可以与另两个端点位于不同源。

使用 jose 签发访问令牌：

import { importPKCS8, SignJWT } from "jose";

const privateKey = await importPKCS8(process.env.HAPPY_SIGNING_KEY!, "ES256");

export async function accessToken(userId: string): Promise<string> {
    return await new SignJWT({})
        .setProtectedHeader({ alg: "ES256", kid: "happy-2026-09" })
        .setIssuer("https://sso.acme.example")
        .setAudience("https://happy.acme.example")
        .setSubject(userId)
        .setIssuedAt()
        .setExpirationTime("15m")
        .sign(privateKey);
}

在稳定的 https URL 上以 JWKS 形式发布公钥，在密钥和令牌头中都包含 kid，轮换时先发布新密钥，再用它签名。在旧密钥签发的所有令牌都过期前，将它保留在 JWKS 中，之后再移除；守护进程会在下次下载时停止接受该密钥。所有端点都必须通过 https 提供服务；明文 http 仅在用于本地测试的回环主机上被允许。

4. 配置守护进程#

按照团队部署模式安装二进制文件并初始化 Tailcat，但不要使用 WorkOS 设置，而是按以下方式编写机器级 happy.toml：

[feature.team]
enabled = true
host = "0.0.0.0"
port = 3000
authentication = "jwt"
owner_user_id = "REPLACE_WITH_OWNER_USER_ID"

[feature.team.jwt]
name = "Acme SSO"
authorization_url = "https://sso.acme.example/oauth/authorize"
token_url = "https://sso.acme.example/oauth/token"
refresh_url = "https://sso.acme.example/oauth/refresh"
client_id = "happy"
scope = "happy offline_access"
issuer = "https://sso.acme.example"
audience = "https://happy.acme.example"
user_id_claim = "sub"
algorithms = ["ES256"]
jwks_url = "https://sso.acme.example/.well-known/jwks.json"
jwks_refresh_interval_sec = 3600

name 是 Happy 应用在登录按钮上显示的名称。省略 refresh_url 可关闭刷新；如果服务器不需要权限范围，则省略 scope。必须且只能配置一种密钥来源：

  • jwks_url = "https://..."：使用已发布的密钥集（推荐）。守护进程在启动时自行下载密钥，随后每隔 jwks_refresh_interval_sec 秒再次下载（范围 60–86,400，默认 3,600），因此无需将密钥写入配置。如果令牌使用守护进程尚未见过的密钥签名，会立即触发下载，最多每 30 秒一次，因此轮换可立即生效。下载失败时，守护进程保留最近一次有效的密钥，并在一分钟后重试；从 JWKS 移除的密钥会在下次成功下载后失效；
  • public_key = """-----BEGIN PUBLIC KEY-----..."""：使用单个 PEM 公钥；
  • secret_env = "HAPPY_TEAM_JWT_SECRET"：使用共享秘密，将其保存在守护进程服务的该环境变量中，绝不写入 happy.toml。

使用 JWT 认证时，不要设置 workos_organization_id、owner_workos_user_id 或 workos_client_id；守护进程会拒绝这种组合。配置错误会使启动停止，并给出可读的提示，因此守护进程未能启动时应查看服务日志。

用户通过认证方式与用户 ID 的组合来标识。从 WorkOS 切换到 JWT 的部署会以全新的成员账号开始；原有 WorkOS 用户仍保存在系统中，但无法通过 JWT 登录。

5. 验证#

在能够访问守护进程的机器上运行以下检查，将 DAEMON 替换为其地址。

  1. 不携带令牌时，发现接口也应响应：

    curl -s "DAEMON/v0/authentication"

    预期返回 "authenticated": false 和一个包含已配置端点及客户端 ID 的 oauth 方法，不包含任何秘密、密钥或 JWKS 内容。

  2. 通过 Happy 应用登录，或手动测试流程：使用回环 redirect_uri、state 和 PKCE 挑战值打开授权 URL，确认浏览器跳转到 redirect_uri?code=...&state=...，然后在令牌端点兑换授权码。

  3. 携带访问令牌调用发现接口，预期返回 "authenticated": true。用户保存个人资料前，userId 始终为 null。

  4. 确认遭篡改、已过期或受众错误的令牌会得到 401，且响应中的 authentication 字段列出相同方法，并确认面向其他受众的令牌会被拒绝。

  5. 如果配置了刷新，执行一次刷新，确认新的访问令牌有效，并在启用轮换时确认旧刷新令牌已被拒绝。

  6. 在 Happy 应用中以所有者身份登录，完成首次设置，并运行已部署节点测试。然后以第二位成员身份登录，确认该成员不是所有者。

故障排查#

  • 浏览器显示错误而没有重定向。重定向 URI 未在授权服务器中注册，或客户端 ID 错误。
  • 兑换授权码失败，返回 invalid_grant。授权码已过期或已被使用，重定向 URI 与授权时使用的不一致，或服务器没有使用 S256 验证 PKCE。
  • 启动后所有访问令牌立即被拒绝。守护进程无法下载 JWKS：检查它能否通过 https 直接访问 jwks_url 而不经过重定向，并查看服务日志中的密钥集警告。
  • 所有访问令牌都被拒绝。将 iss、aud、alg 和 kid 与配置精确比对，并检查服务器时钟。有些身份提供商只有在请求 API 或资源受众时才签发 JWT，否则会签发不透明访问令牌；守护进程需要 JWT。
  • 始终没有发生刷新。未配置 refresh_url，令牌响应中没有 refresh_token，或者权限范围缺少 offline_access 或对应项。
  • 有人意外成为所有者。只有 owner_user_id 与令牌中的用户 ID 声明匹配时，才会赋予所有者身份。

绝不要将真实令牌、授权码、私钥或共享秘密粘贴到对话、问题单或日志中。
